Spring Boot services across many environments

App teamDevOps

A new stand: 30 copied files → 1 file

Situation: 30 Spring Boot services in dev, test, stage and prod, plus a stand for every big client. Each environment holds its own copy of every application.yaml, and the copies slowly drift apart.

Keep what all environments share in application.yaml and only the differences in application.<env>.yaml next to it. A new stand is one file in envs/ that reuses the service list of the base environment.

your-git-repo/
components/orders/application.yaml        # shared by all environments
components/orders/application.prod.yaml   # only what differs in prod
envs/base.yaml                            # which services exist
envs/client-acme.yaml                     # a new stand
envs/client-acme.yaml
include:
  env: base

Result: microconfig -e client-acme builds a plain application.yaml for every service that Spring Boot reads as is. A new stand takes one file plus overrides only where it really differs.

Helm values for every service

DevOpsPlatform team

50 values.yaml with the same blocks → 1 shared component and short service files

Situation: 50 services on Kubernetes, each with its own values.yaml. Probes, resources and the image registry are copy-pasted everywhere, and the port in the chart doesn't always match the port in the application config.

Keep Helm values in *.helm files. Shared defaults live in one component that every service includes, and the port comes straight from the application config.

components/k8s-defaults/values.helmshared
resources:
  limits:
    memory: 512Mi
probes:
  readiness: /actuator/health/readiness
components/orders/values.helm
#include k8s-defaults

replicaCount: 2
image:
  repository: example/${this@name}
service:
  port: ${app::this@server.port}

Result: every service gets a complete build/<service>/values.yaml for helm upgrade -f. Changing the defaults is one edit, and the chart can't disagree with the application about the port.

Company-wide defaults from a platform team

Platform team

12 pull requests per change → 1 commit

Situation: a platform team owns monitoring, logging and tracing settings. Twelve product teams copy them into their services, so every change means twelve pull requests and a few teams that never update.

The platform team keeps shared components, product teams include them. A team can still override a default explicitly, and the override is visible right in its config.

components/platform/monitoring/application.yamlplatform team
monitoring:
  endpoints: health, prometheus
  secure: true
components/orders/application.yamlproduct team
#include monitoring, logging, tracing

name: orders
monitoring.secure: false   # an explicit, reviewable exception

Result: the platform team changes one file, and every service picks it up on the next build. The build diff shows exactly which services changed.

Regions, tenants and other variants of prod

DevOps

2 full copies of prod → 1 profile with the differences

Situation: prod runs in Europe and in the USA. Same services, almost the same config, but different database hosts and a few region settings. Keeping two full copies of prod config means fixing every bug twice.

Create an environment that reuses prod and adds a profile with the regional differences.

envs/prod-usa.yaml
include:
  env: prod      # the same services as prod

profiles:
  - prod          # application.prod.yaml applies
  - usa           # then application.usa.yaml
components/orders/application.usa.yaml
db.host: usa-db.internal

Result: microconfig -e prod-usa takes the base config, then prod overrides, then the USA profile, then application.prod-usa.yaml if a service needs something only there. A fix in prod reaches both regions.

Reviewing config changes before a release

DevOpsApp team

Errors at startup in production → errors in CI

Situation: config changes ship together with the release, and nobody sees their final effect on each service. A renamed key or a typo shows up at startup, in production.

Build configs in CI on every change. A reference to a missing component or key stops the build with the file and line, and every build writes a diff of the result next to each service's configs.

build/payment-frontend/diff-application.yaml
payment-backend:
  path: /api -> /api/v2

Result: a broken config never reaches an environment, and reviewers see what actually changes in the generated files, not only in the sources.

Configs that are not YAML: logback.xml, nginx.conf, Dockerfile

App teamDevOps

N almost identical files → 1 template

Situation: every service needs its own nginx.conf or logback.xml. The files are 95% identical, so they get copied, and then fixed in some services but not in others.

Keep one template with placeholders, and let every service render its own copy.

components/orders/nginx.conftemplate
server {
  server_name ${this@name}.example.com;
}
components/orders/application.yaml
mc.template.nginx: ${this@configDir}/nginx.conf -> nginx.conf

Result: build/orders/nginx.conf with server_name orders.example.com. Move the template to a shared component and every service gets its own version. Mustache sections handle parts that only some environments need.

Starting from configs you already have

Platform teamDevOpsApp team

A big-bang migration → one block at a time, each step proven by an empty diff

Situation: there is already a repository of copy-pasted configs. Nobody wants a big-bang migration that might change something by accident.

Your YAML and properties files are valid Microconfig sources as they are. Put them under components/, list the services in envs/, and build once. Then move one copy-pasted block at a time to a shared component and build again.

Result: after a refactoring that changes nothing in the generated files, the build writes no diff files at all. That is your proof the refactoring was safe, step by step.
